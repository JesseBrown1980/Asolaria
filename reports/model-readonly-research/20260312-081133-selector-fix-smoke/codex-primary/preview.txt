## Ranked root causes
1. Frontend polling overlap is the main destabilizer. `refreshHealth()` has no in-flight guard in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L9340), it runs on intervals in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L13627), and it also triggers cockpit refreshes in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L9390). Gateway audit has its own 20s poll in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L13649) and no separate in-flight guard.
2. Gateway transport/runtime issues are the main degraded-route cause. Each gateway panel refresh fans out into three requests in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L10059), and each server gateway route proxies through `callGatewayControlApi()` in [server.js](/C:/Users/acer/Asolaria/server.js#L4142), which waits for service availability and applies request timeouts. That matches “gateway authority/audit unstable or degraded” much better than profile problems.
3. The false empty cockpit state is a frontend render bug, not a registry/profile bug. The UI paints an empty snapshot in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L13579). Meanwhile the server-side cockpit snapshot is cached with stale fallback in [server.js](/C:/Users/acer/Asolaria/server.js#L10095), [server.js](/C:/Users/acer/Asolaria/server.js#L13444), and [server.js](/C:/Users/acer/Asolaria/server.js#L14792), so the backend is already biased toward stability.
4. Loopback/API authorization is a real gate, but not the main cause in the evidence shown. If the dashboard is accessed via non-loopback host/IP, cockpit and gateway routes will 403 by policy via [server.js](/C:/Users/acer/Asolaria/server.js#L11933). But the verified successful cockpit prompt strongly suggests the tested path is already passing that gate.

## Why profile permissions are or are not central
They are not central.

In the inspected control path, profile JSON is used for identity, memory anchors, abilities, and sidecar paths in [server.js](/C:/Users/acer/Asolaria/server.js#L13049). Those fields are then used to build bootstrap prompt text in [server.js](/C:/Users/acer/Asolaria/server.js#L13230). That is profile identity/ability metadata, not runtime authorization.

The real authorization gates are loopback checks on the API routes in [server.js](/C:/Users/acer/Asolaria/server.js#L11320) and [server.js](/C:/Users/acer/Asolaria/server.js#L11933). The real prompting path is sidecar ensure plus inbox send in [server.js](/C:/Users/acer/Asolaria/server.js#L13669). Helm’s live state in [status.json](/C:/Users/acer/Asolaria/runtime/admin-terminals/helm/status.json) shows `lastInputSource = "Asolaria Dashboard"` and processed inbox lines, which is direct evidence that profile permissions are not blocking prompt delivery.

Profile loading would move up the list only if the registry or profile files were unreadable or mismatched. The registry in [admin-terminal-identities.json](/C:/Users/acer/codex-bridge/profiles/admin-terminal-identities.json) and both profiles in [admin-helm-v1.profile.json](/C:/Users/acer/codex-bridge/profiles/admin-helm-v1.profile.json) and [admin-sentinel-v1.profile.json](/C:/Users/acer/codex-bridge/profiles/admin-sentinel-v1.profile.json) are present and coherent with the running sidecars.

## Minimal ranked fix plan
1. Fix the misleading cockpit empty state first. Replace the startup hard-coded empty render in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L13579) with a loading state or last-known snapshot.
2. Add an in-flight guard to `refreshHealth()` and stop nesting cockpit refresh inside every health refresh in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L9340). Let cockpit polling own cockpit updates.
3. Reduce or pause background polling when the tab is hidden, especially health and gateway audit. The cockpit interval already checks `document.hidden` in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L13634); health and gateway polling should be brought closer to that behavior.
4. Add in-flight guard plus failure backoff to `refreshGatewayAuditPanel()` in [public/app.js](/C:/Users/acer/Asolaria/public/app.js#L10059). One degraded gateway dependency should not keep generating repeated slow proxy calls.
5. If more stabilization is still needed, move routine background status to `/api/health/fast` and keep deeper health reads less frequent or user-driven.

## Risks and unknowns
- This packet supports the diagnosis strongly, but it does not include a full browser network trace or gateway-control log timeline, so the exact weight of poll amplification versus gateway-service slowness is inferred.
- If the dashboard is sometimes opened through a non-loopback host, loopback-only routes can still fail by policy. That would be a separate access-path issue, not a profile-permission issue.
- Sentinel’s prompt ingress is less directly verified than Helm’s in the current evidence set.
- A secondary intermittent PowerShell/tooling issue is still possible, but the existing Helm inbox evidence makes it unlikely to be the primary remaining problem.
