Asolaria Systems Engineering Assessment
A systems engineer rebuilding a "civilization program" — one that absorbs, watches, decomposes, and simplifies external programs while keeping itself alive — would inventory these 16 domains:
Findings By Domain
1. Process Lifecycle & Supervisory Control
Current state: startAsolariaServers() (server.js:35198) is the single entry point. Boot sequence:
warmAsolariaRuntime() — bootstraps guardian profile, warms Playwright screenshot worker
Express app.listen(port) on 4781
Post-listen (async): MQTT broker start → MQTT bridge start → health cache warm → civilization world warm → super coder cockpit warm
Deferred (900ms): external observed prune scheduler, model audit scheduler, Telegram polling, colony watchdog, voice bridge orchestrator
Brain leader selection loop (if STARTUP_BACKGROUND_TASKS_ENABLED)
HTTPS server on secondary port (if certs available)
Raw probe server on 4782 (minimal startup mode)
Keepalive: Keep-Asolaria-HealthGuardrail.ps1 — periodic HTTP/HTTPS/OLI probe, bridge message on failure, state persistence. Colony watchdog (syncAgentColonyWatchdogScheduler) with setInterval ticks.
GAP: No process supervisor (systemd/pm2/Windows service). No graceful shutdown handler (process.on('SIGTERM') not found). No automatic restart on crash. Watchdog is an external PowerShell script that must be launched separately.
UPGRADE: Add a proper process manager, graceful shutdown with drain, and a Windows service wrapper.
2. IPC & Message Bus
Current state:
MQTT (aedes broker, local): Embedded via mqttLocalBrokerManager.js. Supports WS/WSS for browser realtime. Publishes health, colony, presence, and world snapshots to topic tree.
Relay room (asolaria_bridge): codex-bridge sends/receives messages between agents via Node.js child process + bridge.js.
EventEmitter (graphRuntimeEmitter): Internal pub/sub for graph events, max 64 listeners.
HTTP/Express: Primary IPC — everything routes through the gateway.
GAP: No message durability (MQTT QoS 0 likely). MQTT bridge failure is logged but not retried. No dead-letter queue. EventEmitter is in-process only — if the process dies, events are lost.
UPGRADE: Add MQTT QoS 1/2 for critical messages, persistent sessions, retry logic on bridge disconnect.
3. State Persistence & Recovery
Current state: 9 disk-backed stores, all using atomic write (tmp + rename):
memory.json (170KB) — turns with snapshots every 5min, keeps 24 snapshots
task-ledger.json (1.5MB) — tasks + events
projects.json (2.7KB) — project registry
mistake-ledger.ndjson (625KB) — append-only raw log
mistake-patterns.json (22KB) — extracted patterns
graph-runtime-events.ndjson (1MB) — observation events
workspace-semantic-index.json (7.4MB) — Gemini embeddings
skills-tools-index.json (70KB) — unified index
guardian-approvals.json (42KB) — approval requests
All vault secrets in data/vault/{owner,asolaria}/vault.secrets.json.
GAP: No WAL (write-ahead log). No transactional writes across stores. Corruption recovery is "backup the broken file and reset to empty" — data can be lost. No replication.
UPGRADE: Add WAL or SQLite for critical stores. Cross-store consistency checks. Periodic integrity verification.
4. Resource Management & Limits
Current state:

Tasks: max 4000, events max 12000
Projects: max 500
Job queue: max 500 jobs, concurrency 2
Snapshots: max 24 kept

GAP: No Node.js heap monitoring. No disk usage alerts. tmp file sprawl (many .tmp-* files if process crashes mid-write). No memory pressure backoff. workspace-semantic-index.json is 7.4MB loaded fully into memory.
UPGRADE: Add heap/disk metrics, backpressure on job queue, GC for orphaned tmp files.
5. Error Handling & Resilience
Current state:
Brain fallback chain (brainOrchestrator.js): Sequential attempt through configurable provider order (default: anthropic → codex → gemini-api → vertex → gemini-cli → openclaw → openai → cursor → antigravity). Falls back on 429/quota/timeout/auth errors. Hard-stops on guardian-blocked/denied. Terminal fallback: buildLowCostResponse() returns a canned message.
shouldFallbackToAlternateProvider(): Pattern-matches error text to decide skip vs throw.
Each provider attempt is recorded as a graph event.
GAP: No circuit breaker pattern (a broken provider is retried every time). No exponential backoff. No health-based routing (always tries in order). No retry count limit per request.
UPGRADE: Add circuit breakers with half-open recovery, provider health scores, exponential backoff.
6. Security Boundaries
Current state:
Vault (secureVault.js): AES-256-GCM, two namespaces (owner/asolaria). Master keys stored as plaintext base64 on disk.
Risk engine (riskEngine.js): Numeric score per action (0-9 baseline), plus regex-based text analysis for destructive ops, secrets, money, mass posting, security incidents, CAPTCHA, privilege escalation. Score → level (low/medium/high/critical).
Edge risk engine (edgeRiskEngine.js): Same scoring for graph event edges, with cross-domain and approval-state bonuses.
Brain safety prefix (brainPolicy.js): Injected into every brain prompt — ClawBot adversary warning, no credential sharing, CAPTCHA escalation, minimal tools preference.
Guardian (guardianStore.js, guardianApprovalStore.js): Owner profile with contacts, approval requests with expiration (5-180 min), SHA-256 dedup.
Approval engine (approvalEngine.js): Command-prefix-based auto-approval, read-only detection, destructive detection, persistent prefix whitelist.
Secret redaction in memoryStore: PEM keys, Google API keys, JSON secret fields, auth headers, hex tokens.
GAP: Master keys on disk in plaintext. No RBAC (all-or-nothing owner model). No network-level auth on Express endpoints (anyone on the network can call the API). No TLS client cert validation. Approval engine uses substring matching, not AST-level analysis.
UPGRADE: Encrypt master keys with OS keychain. Add API key/token auth to gateway. RBAC for multi-operator scenarios. Move to AST-based command analysis.

Warp doesn't publicly document the internals of how the 'auto' model selection works, so I can't give you specifics on their implementation.
But I can speak to the general problem you're describing—it's a well-known challenge in multi-agent/multi-model systems:
Why local multi-model setups collapse:
•  No clear authority hierarchy — if every model can evaluate whether it should handle a task, they compete rather than cooperate.
•  Context window limits — when one model hits its limit, handing off cleanly to another without losing context is hard.
•  Self-promotion bias — LLMs tend to be confident they can handle things, so they all "volunteer."
What typically works better (and likely what Warp does):
•  A lightweight classifier/router sits above the models — it's not an LLM itself (or it's a very small, constrained one). It decides which model handles the task before any model sees the prompt.
•  Models never choose for themselves — the routing decision is external, not democratic.
•  Single model per task — rather than running 5 models simultaneously, one model is selected per request.
So the key insight is: don't let the models decide who's in charge. Use a separate, deterministic (or near-deterministic) routing layer that dispatches to exactly one model per task. The models should never even know other models exist.

How It Works

Key resolution (in priority order):

4. Legacy key file: data/vault.master.key (auto-copied to namespace on first use)
5. If nothing exists: auto-generates a random 32-byte key and writes it

Here's the full report on the six subsystems you asked about.
1. Memory (memoryStore.js → data/memory.json)
A disk-backed conversation memory store. Turns (user/assistant/system) are appended to an in-memory array, then flushed to memory.json (~170 KB currently).
Key mechanics:
•  Each turn has id, role, text, images, files, meta (can carry chatId/conversationId for thread routing), and at timestamp.
•  Max turns: configurable via env, default 300. When exceeded, oldest turns are spliced out (rolling window).
•  Snapshots: Every 5 minutes (configurable), it writes a memory.snapshot.*.json sidecar. Keeps last 24 snapshots, auto-prunes older ones.
•  Backups: If the file can't be parsed, it copies the corrupt blob to memory.corrupt.*.json and resets to empty. Manual backups also supported.
•  Merge logic: On save, it reads the current disk state and the in-memory state, deduplicates by turn ID (newer timestamp wins), sorts chronologically, then writes atomically (write-to-tmp + rename).
•  Secret redaction: Before storing text, it runs regex-based redaction for PEM keys, Google API keys (AIza...), JSON secret fields, auth headers, hex tokens, and natural-language password patterns.
•  Boilerplate filtering: Has patterns to detect and optionally hide "Asolaria Brain mode active" boilerplate turns.
•  Compaction: There's a term-frequency analysis system that tokenizes turns, removes stopwords, and extracts top terms — used for generating compact memory summaries.
•  Conversation threading: Turns can be filtered by chatId from turn metadata, enabling multi-conversation support.
2. Tasks (taskLedgerStore.js → data/task-ledger.json)
A full task management system — the ledger file is ~1.5 MB, meaning it's accumulated a lot of data.
Key mechanics:
•  Task schema: id, title, description, status, priority, owner, source, tags, progress (0-100), dueAt, startedAt, completedAt, archived, projectScope.
•  Statuses: planned → ready → in_progress → blocked → review → done → canceled → archived. Business logic auto-sets startedAt on in_progress, completedAt on done, caps progress at 99 if not done, forces 100 on done.
•  Priorities: low, normal, high, critical.
•  Events: Separate event log within the same file. Each event links to a taskId with type, actor, source, note, detail. Acts as an audit trail.
•  Limits: Max 4000 tasks, 12000 events (env-configurable).
•  Project scoping: Tasks can be filtered by projectScope or a text projectMarker (searches title/description). This connects tasks to the project registry.
•  Graph integration: Task changes emit events to the graphRuntimeStore for the observation graph.
•  Atomic writes: Same tmp+rename pattern as memory.

How They Connect
The subsystems form a knowledge graph pipeline:
1. Memory captures conversation turns → feeds into the semantic knowledge store (uses Gemini embeddings for vector search over conversation + workspace files → stored in workspace-semantic-index.json at 7.4 MB).
2. Tasks are scoped to Projects via markers and projectScope fields. Task events flow into the graph runtime store (graph-runtime-events.ndjson, ~1 MB) which is an observation event log with risk scoring.
3. Skills define multi-step workflows whose steps are executed by the skill runner. Skills and their actions are cross-referenced in the skills-tools-index.
4. Mistakes are logged as raw entries, then auto-promoted to patterns that link back to skills/tools/activities. These patterns generate avoidance hints that can be fed back into the brain's prompt.
5. The skills-tools-index ties everything together: it combines skill metadata, action risk scores, Codex skill discovery, mistake pattern cross-links, and MCP provider status into a single queryable index.
It's an ambitious self-improving loop: the system tracks its own mistakes, links them to the tools/skills that caused them, generates avoidance guidance, and feeds that back into decision-making.

What a Systems Engineer Would Collect — and What I Found
I audited Asolaria across 16 domains that a systems engineer would inventory before rebuilding a self-sustaining "civilization program." The full plan has detailed findings per domain. Here's the high-level picture:
What's Strong
•  Self-improvement loop is genuinely complete: mistake ledger → pattern extraction → avoidance hints → brain prompt injection. Most systems don't have this at all.
•  Brain fallback chain with 9 providers and graph-event recording of every attempt is solid observability.
•  Security layering is thoughtful: risk scoring on every action, brain safety prefix, guardian approvals, secret redaction in memory, CAPTCHA escalation.
•  Atomic writes everywhere (tmp + rename). No half-written files.
•  Skill architecture is well-designed: JSON descriptors, risk per step, permissions, registry caching.
•  Civilization world model with districts, entities, and motion states is an interesting abstraction.
Critical Gaps (Top 5)
1. 35,000-line monolith (server.js). This is the #1 rebuild blocker. Everything is tangled together.
2. No process supervisor or graceful shutdown. If Node crashes, everything is lost — in-memory job queue, scheduler state, active requests.
3. No API authentication. Anyone on the network can call any endpoint.
4. No program absorption pipeline. The "absorb and simplify programs" vision has 4 codebase-review skills but no AST parser, dependency graph builder, or automated decomposer.
5. Master keys in plaintext on disk.
7 "Future Skills" for the Civilization Program
The plan includes upgrade potentials: AST Decomposer, Program Absorber, Self-Healer, Civilization Pruner, Provider Health Oracle, Config Migration, and Distributed Scheduler. These are the capabilities that would turn Asolaria from an orchestrator into something that can actually absorb and simplify other programs.
