========================================================
ROOT CAUSE: FIELD NAME MISMATCH — `client` vs `clientId`
========================================================

The Mongoose UserSchema (User.ts line 180-183) defines the field as:

    client: { type: Schema.Types.ObjectId, ref: 'Client' }

The hydrateUser function (Endpoint.ts line 78) reads it as:

    clientId: user!.client!.toHexString() || ''

This means the MongoDB document MUST have a field named `client` (not `clientId`)
containing a valid ObjectId.

However, the dev-bypass session (dev-bypass.ts line 31) sets:

    clientId: '69c3ecbdecd240dd83e93d3b'

This is the SESSION shape — fine for the cookie. But the QUESTION is whether
the actual MongoDB document with _id '69c3ecbdecd240dd83e93d3d' was seeded
with field `client` or `clientId`.

========================================================
THE CRASH PATH (step by step)
========================================================

1. User hits /api/auth/dev-bypass → session cookie gets set with
   session.user.id = '69c3ecbdecd240dd83e93d3d'

2. User hits any protected EZ Protect endpoint

3. Endpoint.register() (line 264-268) reads session:
   session.user → UserSessionTUser { id: '69c3ecbdecd240dd83e93d3d', ... }

4. hydrateUser(user) is called (line 285) with that session user

5. Line 57: models.UserModel.findById('69c3ecbdecd240dd83e93d3d')
   → THIS IS THE FIRST FAILURE POINT.
   If no document with this _id exists in MongoDB, `user` is null.

6. Line 78: user!.client!.toHexString()
   → THIS IS THE SECOND FAILURE POINT.
   If the document exists but was seeded with `clientId` instead of `client`,
   then user.client is undefined → .toHexString() throws → 500.

7. Line 82-102: user!.permissions.map(p => { ... p.location.toHexString() })
   → THIS IS THE THIRD FAILURE POINT.
   If permissions was seeded as a flat object { ezProtect: {...} } instead of
   an array of { location: ObjectId, ezProtect: {...}, ... } objects,
   .map() throws or .location is undefined → 500.

========================================================
WHAT dev-bypass.ts SEEDS INTO SESSION (NOT MongoDB)
========================================================

The dev-bypass only sets the SESSION COOKIE. It does NOT insert a document
into MongoDB. So if nobody separately inserted a User document with
_id: ObjectId('69c3ecbdecd240dd83e93d3d') into the users collection,
findById returns null and everything after line 57 crashes with:
  "Cannot read properties of null (reading '_id')"

========================================================
DIAGNOSIS
========================================================

There are TWO bugs:

BUG 1 (CRITICAL): No MongoDB user document exists.
  The dev-bypass.ts sets a session cookie but never creates a MongoDB document.
  hydrateUser calls findById → null → crash on line 69 (user?._id.toHexString)
  or line 71 (user!._id.toHexString).

BUG 2 (STRUCTURAL): If the user WAS seeded manually with `clientId` instead
  of `client`, Mongoose ignores the field for the `client` path.
  user.client would be undefined → line 78 crashes.

BUG 3 (STRUCTURAL): If permissions were seeded as a flat object instead of
  an array of {location: ObjectId, ...} subdocuments, .map() fails or
  p.location is undefined.
