1. WHAT IS SYMPHONY
============================================================

Symphony is OpenAI's multi-agent orchestration system that turns project work
(Linear issues) into isolated, autonomous coding agent runs. It is a long-running
daemon that:

  1. Polls Linear for candidate issues (Todo, In Progress, Merging, Rework)
  2. Creates an isolated git-cloned workspace per issue
  3. Launches OpenAI Codex in app-server mode inside each workspace
  4. Sends a workflow prompt (from WORKFLOW.md) to Codex
  5. Keeps Codex working until the issue is done or blocked
  6. Manages retries, reconciliation, terminal state cleanup

Status: "low-key engineering preview for testing in trusted environments"
License: Apache 2.0

The SPEC.md (language-agnostic) is designed so anyone can build Symphony in any
language. The Elixir implementation is their reference.

7. AGENT RUNNER (lib/symphony_elixir/agent_runner.ex)
============================================================

Executes a single Linear issue in an isolated workspace with Codex.

Flow:
  1. Workspace.create_for_issue(issue)
  2. Workspace.run_before_run_hook(workspace, issue)
  3. AppServer.start_session(workspace)
  4. Loop: run_codex_turns up to max_turns (default 20)
     - Turn 1: full prompt from PromptBuilder
     - Turns 2+: continuation guidance prompt
     - After each turn: check if issue still in active state
     - If active + under max_turns: continue
     - If terminal or max_turns reached: stop
  5. AppServer.stop_session(session)
  6. Workspace.run_after_run_hook(workspace, issue)

Key: multi-turn within a single Codex app-server session. The session
stays open across turns (same thread), only the prompt changes.

9. ORCHESTRATOR (lib/symphony_elixir/orchestrator.ex)
============================================================

GenServer that owns the polling loop and all runtime state.

State:
  - poll_interval_ms (from WORKFLOW.md, default 30s)
  - max_concurrent_agents (default 10)
  - running: %{issue_id => running_entry}
  - claimed: MapSet of reserved issue IDs
  - completed: MapSet of finished issue IDs
  - retry_attempts: %{issue_id => RetryEntry}
  - codex_totals: aggregate token/runtime counters
  - codex_rate_limits: latest rate limit snapshot

Poll cycle:
  1. Refresh runtime config (hot-reload from WORKFLOW.md)
  2. Validate config (tracker kind, API token, project slug, codex command)
  3. Reconcile running issues (check if moved to terminal state)
  4. Reconcile stalled sessions
  5. Fetch candidate issues from Linear
  6. Choose issues to dispatch (priority sort, concurrency limits, per-state limits)
  7. Spawn agent tasks via Task.Supervisor

Retry: exponential backoff (base 10s, max 300s)
Continuation: 1s delay for re-check after normal completion

Worker exit handling:
  - :normal → schedule continuation check (issue may still be active)
  - other → schedule retry with exponential backoff

Reconciliation:
  - Terminal state → stop agent + cleanup workspace
  - No longer routed to worker → stop agent
  - Non-active state → stop agent
  - Active state → refresh issue data in running entry

11. WORKFLOW.MD (the actual workflow contract)
============================================================

YAML frontmatter config:
  tracker:
    kind: linear
    project_slug: "symphony-0c79b11b75ea"
    active_states: [Todo, In Progress, Merging, Rework]
    terminal_states: [Closed, Cancelled, Canceled, Duplicate, Done]
  polling:
    interval_ms: 5000
  workspace:
    root: ~/code/symphony-workspaces
  hooks:
    after_create: git clone --depth 1 + mise trust + mix deps.get
    before_remove: mix workspace.before_remove
  agent:
    max_concurrent_agents: 10
    max_turns: 20
  codex:
    command: codex --config shell_environment_policy.inherit=all
             --config model_reasoning_effort=xhigh
             --model gpt-5.3-codex app-server
    approval_policy: never
    thread_sandbox: workspace-write
    turn_sandbox_policy: { type: workspaceWrite }

Prompt body defines a full autonomous workflow:
  - Step 0: Determine ticket state and route
  - Step 1: Start/continue execution (workpad management)
  - Step 2: Execution phase (implement, validate, PR)
  - Step 3: Human Review and merge handling
  - Step 4: Rework handling
  - PR feedback sweep protocol
  - Blocked-access escape hatch
  - Workpad template (## Codex Workpad)

Key concepts:
  - Single persistent "## Codex Workpad" comment per issue
  - Uses Liquid/Solid templates: {{ issue.identifier }}, {{ issue.title }}, etc.
  - Skills: linear, commit, push, pull, land
  - Status map: Backlog → Todo → In Progress → Human Review → Merging → Done
  - Rework = full approach reset (close PR, fresh branch, start over)

14. KEY ARCHITECTURE PATTERNS
============================================================

OTP Supervision tree:
  SymphonyElixir.Supervisor (one_for_one)
  ├── Phoenix.PubSub (SymphonyElixir.PubSub)
  ├── Task.Supervisor (SymphonyElixir.TaskSupervisor)
  ├── WorkflowStore        — hot-reloading WORKFLOW.md cache
  ├── Orchestrator          — main polling/dispatch GenServer
  ├── HttpServer            — optional Phoenix endpoint
  └── StatusDashboard       — terminal UI GenServer

Hot reload: WorkflowStore polls WORKFLOW.md every 1s, checks mtime+size+hash.
Changes take effect on next poll cycle without restart.

Tracker abstraction: SymphonyElixir.Tracker behaviour with two adapters:
  - "linear" → SymphonyElixir.Linear.Adapter
  - "memory" → SymphonyElixir.Tracker.Memory (for testing)

Workspace isolation: Each issue gets its own directory under workspace.root,
named by sanitized issue identifier. Hooks run in workspace context.

Template engine: Solid (Liquid-compatible) for prompt rendering.

Token accounting: Absolute totals from thread/tokenUsage/updated preferred.
Never count deltas. See docs/token_accounting.md.

17. RELEVANCE TO ASOLARIA
============================================================

Symphony and Asolaria share deep architectural DNA:

SYMPHONY                          ASOLARIA
─────────                         ────────
Orchestrator GenServer             → omnispindle.js
WORKFLOW.md prompt contract        → spawnContextBuilder.js + IX entries
Linear adapter                     → intentRouter.js + MQTT
Workspace isolation per issue      → admin-terminals per agent
Agent Runner (Codex app-server)    → connectors (anthropic, codex, gemini, cursor)
Status Dashboard                   → phone-mode UI / admin terminal screens
Hot-reload WorkflowStore           → runtime/ live config
Task.Supervisor for agents         → workerRouter.js
Retry with exponential backoff     → existing retry logic
Dynamic tools (linear_graphql)     → MCP tools / skill.json

Key differences:
  - Symphony is Elixir/OTP; Asolaria is Node.js
  - Symphony is single-tracker (Linear); Asolaria is multi-connector
  - Symphony uses Codex only; Asolaria supports Claude, Gemini, Codex, Cursor
  - Symphony is stateless (no DB); Asolaria has memoryStore + agent index
  - Symphony has no federation; Asolaria has cross-colony (Liris, Felipe, etc.)

Patterns worth absorbing:
  1. WORKFLOW.md contract — versioned prompt + config in one file
  2. Hot-reload config without restart
  3. Per-issue workspace isolation with lifecycle hooks
  4. Multi-turn continuation within single session
  5. Structured retry with exponential backoff + continuation checks
  6. Issue state reconciliation (stop agents when issue moves to terminal)
  7. Token accounting strategy (absolute totals, never deltas)
  8. The "land" skill loop (conflict → fix → CI → merge → done)
