1. EvaluateEzProtectAlerts/UseCase.unit.ts — GRADE: A-
------------------------------------------------------------------------

STRENGTHS:
  - All 5 trigger types tested (result_state, control_failure, calibration_failure,
    pm_failure, threshold, device_offline)
  - Threshold: all 5 operators tested (gt, gte, lt, lte, eq) including boundary
  - Deduplication tested (recent alert skips firing)
  - Email delivery: success, failure (non-fatal), both channel, sms-only, empty
    recipients
  - Alert history shape validated with objectContaining
  - Device offline: default minutes, missing deviceModel, locationId omission
  - Unknown trigger type handled
  - Multiple rules evaluated correctly
  - buildAlertMessage: faqLinks, videoLinks, device_offline message with details

COVERAGE GAPS:
  - No test for disabled rules (enabled: false) — the source filters by
    {enabled: true}, but no test verifies disabled rules are excluded.
  - No test for rules with locationId: null/$exists:false matching the $or filter.
    The source queries {$or: [{locationId}, {locationId: {$exists: false}},
    {locationId: null}]} but tests only use matching locationId.
  - No test for alert history creation failure (e.g., create() throws). This
    path is NOT wrapped in try/catch in the source — it would propagate up
    and return Result.fail. This is potentially a BUG: a single failed
    history write kills the entire evaluation loop.
  - No test for sendPlainEmail throwing (vs returning Result.fail). The mock
    uses mockResolvedValue(Result.fail(...)) but never mockRejectedValue.
    If sendPlainEmail throws, the error propagates differently.
  - The email failure test asserts console.error with `expect.any(Error)` but
    the source passes `emailResult.error` which is the Result error string,
    not an Error object. This assertion may be fragile.
  - No test for events with multiple matching result states (e.g., one event
    matches two rules of different trigger types).

MOCK REALISM:
  - Mocks are realistic. lean() chaining matches Mongoose patterns.
  - The `null as any` for queue parameter is fine since alerts don't use queue.

POTENTIAL FALSE POSITIVES:
  - The aggregate mock in device_offline tests returns static data. The test
    verifies the aggregate was called but does NOT verify the pipeline shape
    (except for the locationId omission test). If the pipeline changes, tests
    still pass.

================================================================================
 CROSS-CUTTING ISSUES
================================================================================

1. MISPLACED FILE (CRITICAL):
   repos/EzProtectRepo.unit.ts contains domain tests, not repo tests.
   The actual EzProtectRepo class (650+ lines, 6 public methods, complex
   aggregation pipelines) has ZERO unit test coverage.

2. NO INTEGRATION TESTS FOR QUEUE-SERVER USE CASES:
   All queue-server tests are unit tests with mocked DB. No integration
   tests verify actual MongoDB queries, aggregation pipelines, or upsert
   behavior. The EzProtectRepo's aggregation pipeline in
   getCorporateDashboard is particularly complex and error-prone.

3. @ts-nocheck IN INTEGRATION TESTS:
   Both route.int.ts files use @ts-nocheck, suppressing type checking.
   This risks missing type regressions in the API layer.

4. PARSER ALIAS COVERAGE:
   The normalizeResultState function has 14 aliases mapped to 8 canonical
   states. Only 2 are tested (NEG, WEIRD_STATE). This is the most likely
   place for real-world breakage when Charm devices send variant strings.

5. CSV EDGE CASES UNDER-TESTED:
   - Windows line endings (\r\n)
   - Escaped quotes in quoted fields ("")
   - Header-column mismatch
   - Non-numeric values in numeric columns
   - Alternate header formats (DeviceSerial, TestCode, etc.)

6. NO CONCURRENCY TESTS:
   ProcessEzProtectFile processes events sequentially in a for loop.
   No test verifies behavior if two files are processed simultaneously
   for the same facility (race condition on default alert rule creation).
