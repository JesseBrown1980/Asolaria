Branch triggers:
  - default (PRs):      Build all 4 apps (PUBLISH=0, build-only verification)
  - {master}:           Build + Push all 4 apps to DigitalOcean Container Registry (PUBLISH=1, PRERELEASE=1)
  - {release/*}:        Build + Push all 4 apps (same as master, PRERELEASE=1)
  - {production}:       Build + Push all 4 apps (PUBLISH=1, no prerelease)

Build logic (reusable anchor cmd_build_maybe_push):
  1. Turbo dry-run to detect if app is affected since BASE_SHA
  2. Skip build if not affected (unless FORCE_BUILD=1)
  3. Turbo prune --scope=$APP --docker to create minimal Docker context
  4. Install deps in pruned workspace (pnpm install --frozen-lockfile, fallback --no-frozen-lockfile)
  5. Build with NODE_OPTIONS="--max-old-space-size=4096"
  6. Extract version from app package.json
  7. Docker build with app-specific Dockerfile
  8. Push to registry.digitalocean.com/${REGISTRY}/<repo-name> if PUBLISH=1
  9. Skip push if tag already exists in registry

7. IDENTIFIED GAPS AND ISSUES
================================

[GAP-1] PNPM VERSION MISMATCH
  package.json engines: pnpm ^10.0.0, packageManager: pnpm@10.32.0
  CI pipelines + Dockerfiles: pnpm 9.12.2
  Risk: lockfile format incompatibility, different resolution behavior

[GAP-2] ROOT DOCKERFILE IS STALE
  Uses yarn (not pnpm), no turbo prune, no build step
  Likely a leftover from pre-monorepo era. Should be deleted or updated.

[GAP-3] LEGACY DUPLICATE DOCKERFILE
  apps/sync-server/src/Dockerfile duplicates apps/sync-server/Dockerfile
  The src/ version has no pnpm setup, no apt-get, no build tools — would fail if used.

[GAP-4] SENTRY RELEASE PIPE UNUSED
  The x_pipe_sentry anchor is defined but never referenced (*pipe_sentry not used anywhere).
  Sentry releases are NOT being created on deploy. Source maps upload is also disabled.
  Result: Sentry will show unversioned/unlinked errors in production.

[GAP-5] SENTRY SOURCE MAPS DISABLED
  CI explicitly sets SENTRY_UPLOAD_SOURCE_MAPS=false, SENTRY_DISABLE_AUTO_UPLOAD=true
  web-ebacmap sentry config: sourcemaps.disable=true, deleteSourcemapsAfterUpload=true
  Error stack traces in Sentry will show minified code, not original source.

[GAP-6] HARDCODED ENV VARS IN DOCKERFILES
  queue-server/Dockerfile and sync-server/Dockerfile set ENV vars like MONGODB_URI,
  TWOFISH_KEY etc. These are overridden by docker run -e at deploy time, but the
  Dockerfile ENV lines bake empty values into the image layer — a minor security concern.

[GAP-7] NO AUTOMATED TESTS IN CI
  No test step in any pipeline branch (default, master, release, production).
  jest, cypress, and ez-protect test configs exist but are never executed in CI.
  Linting and type-checking also absent from pipeline.

[GAP-8] NO HEALTH CHECK AFTER DEPLOY
  SSH-based deploys (queue-server, sync-server) do docker run but no verification
  that the container started successfully or passes health checks.

[GAP-9] EZ PROTECT FEATURE FLAG NOT IN CI ENV
  NEXT_PUBLIC_FEATURE_CHARM_EZP_MODULE is only in .env.local (test env).
  Not set in any CI/CD pipeline or deployment env var list.
  However, the code now uses permission-based access (not the flag),
  so this is LOW RISK. The flag is effectively vestigial.

[GAP-10] DOCKER PRUNE -a -f ON EVERY DEPLOY
  Every SSH deploy runs "docker system prune -a -f" before starting containers.
  This removes ALL unused images on the host. If multiple apps share a VPS,
  a queue-server deploy would nuke cached images for other containers.

[GAP-11] NO docker-compose.yml
  No docker-compose file exists. Local dev relies on running services individually.
  Multi-service local testing requires manual coordination.

[GAP-12] SECRET_COOKIE_PASSWORD IN CI
  The build step exports SECRET_COOKIE_PASSWORD from env var into the build process.
  This is used during Next.js build (SSR pages). If the value differs between build
  and runtime, iron-session cookies will be invalid.
