1. UNHANDLED ASYNC IN forEach — SILENT FAILURES (Queue.ts + multiple use cases)
   ──────────────────────────────────────────────────────────────────────────────
   Files:
     - Queue.ts line 247: swabSchedules.forEach(async (swabSchedule) => { ... })
     - ImportTestResult/UseCase.ts line 643: swabSchedules.forEach(async ...)
     - ImportTestResult/UseCase.ts line 651: singleMultiCombined.forEach(async ...)
     - CheckSwabsForCompletedTests/UseCase.ts line 247: swabSchedules.forEach(async ...)
     - CheckSwabsForCompletedTests/UseCase.ts line 254: singleMultiCombined.forEach(async ...)

   Problem: Array.forEach does NOT await async callbacks. The async lambdas
   fire-and-forget. Any rejection inside is an unhandled promise rejection that
   will crash Node in newer versions (--unhandled-rejections=throw, default
   since Node 15+). Even if it doesn't crash, the database writes inside
   (updateScheduledDate, ActivityLogModel.create, SwabScheduleModel.updateOne)
   race against each other and against the caller that already returned.

   The code at CheckSwabsForCompletedTests line 305 calls
   `await this.commmitSwabSchedule(swabSchedule, models)` INSIDE a
   forEach-async, meaning the commit fires before the inner
   forEach-async that populates `changes` has finished. The schedule is
   committed with EMPTY or PARTIAL changes.

   Impact: PRODUCTION BUG. Swab schedule dates may not be marked complete.
   Activity logs may be created with empty change records. Corrective actions
   may not trigger. Data corruption is possible under concurrent load.

   Fix: Replace .forEach(async ...) with for...of loops, or use
   Promise.all(array.map(async ...)).

2. STARTUP INIT forEach SWALLOWS ERRORS (index.ts line 105)
   ──────────────────────────────────────────────────────────────────────────────
   ```
   environments.forEach(async env => {
     ...
     await queue.startQueue();
   });
   ```
   Same forEach-async pattern. If startQueue() or initDbMonitoring() throws,
   the promise rejection is UNHANDLED. The outer try/catch on line 104 will
   NOT catch it because forEach returns void immediately.

   Impact: If one environment's DB is unreachable at startup, the server
   continues running but that queue silently never started. No alert, no log
   beyond a Sentry capture deep inside getConnection().

   Fix: Use for...of with await, or Promise.allSettled().

3. queueJob CLOSES ITS OWN CONNECTION (Queue.ts line 176-178)
   ──────────────────────────────────────────────────────────────────────────────
   ```
   if(this.connection) {
     await closeDbConnection(this.appEnv);
     this.connection = null;
   }
   ```
   After every queueJob() call, the shared DB connection is closed. This means
   the next processJobs() tick must re-establish the connection. Worse, if
   processJobs() is running concurrently (setInterval fires while a job is
   processing), the connection gets pulled out from under the running job.

   Impact: Intermittent "connection closed" errors in production. Performance
   degradation from constant reconnection overhead.

   Fix: Remove the closeDbConnection call from queueJob. Let the connection
   persist like it does everywhere else. Only close on stopQueue().

4. shouldLock() CALLED WITHOUT await (Queue.ts line 231)
   ──────────────────────────────────────────────────────────────────────────────
   ```
   if (!this.shouldLock()) {  // shouldLock returns Promise<boolean>
   ```
   shouldLock() is declared `async` (returns Promise<boolean>). Calling it
   without await means the if-check always evaluates a truthy Promise object,
   so the lock check NEVER blocks. The maxConcurrentJobs limit is effectively
   bypassed in processJobs.

   Impact: Multiple jobs can run concurrently beyond the configured limit,
   defeating the purpose of the concurrency guard.

   Fix: Add await: `if (!(await this.shouldLock()))`.

5. Date.now().valueOf() BUG (Queue.ts line 259)
   ──────────────────────────────────────────────────────────────────────────────
   ```
   const lockDeadline = new Date(Date.now().valueOf() - 600000);
   ```
   Date.now() returns a number. Calling .valueOf() on a number is a no-op so
   this works by accident, but it's misleading. Same pattern on line 492. Not
   a runtime bug but indicates confused intent.

6. RACE CONDITION: getNextJob lock-then-update (Queue.ts lines 307-317)
   ──────────────────────────────────────────────────────────────────────────────
   The aggregation pipeline finds a candidate job, then a separate updateOne
   sets lockedAt. Between the aggregate and the updateOne, another queue
   instance (e.g. another container) could pick up the same job. The lock
   should use findOneAndUpdate with atomic filter.

   Impact: In multi-instance deployments, the same job can be processed twice.
