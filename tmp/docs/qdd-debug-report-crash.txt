3. ERROR FLOW ANALYSIS
-----------------------
  The page [id].tsx (apps/web-ebacmap/src/pages/reports/[id].tsx) has two
  error handling layers:

  Layer 1 — In-page error handler (line 167-218):
    Checks `reportError` from useService/SWR. If error has `.status === 404`,
    shows "Report not found". If `.status === 500`, shows "Failed to load
    report data". Otherwise shows generic "An error occurred while loading
    this report".

  Layer 2 — Sentry ErrorBoundary in _app.tsx (line 114-123):
    Shows "An error has occurred. Please refresh the page."
    This catches unhandled React render crashes.

  THE PROBLEM: fetchJson (src/utils/fetchJson.ts) swallows most API errors:
    - On 500: returns false (line 114)
    - On thrown ResponseError: catch block (line 143) shows alert, returns false (line 159)
    - SWR receives data=false, never sets error
    - report?.id is undefined (false?.id), page shows <Loading /> forever
    - OR: if report is falsy but not undefined, accessing report.sections
      in the render path can crash, triggering the Sentry ErrorBoundary

  The user sees "An error has occurred" from the Sentry boundary, NOT the
  in-page error handler at line 167. This means either:
    a) fetchJson returns false, SWR has data=false (truthy!), report=false,
       and report.sections crashes on render, OR
    b) The ResponseError thrown by fetchJson propagates to SWR as error but
       lacks a .status property (it has .response.status instead), and some
       other render path crashes

  ROOT CAUSE: The report ID does not exist. The page doesn't gracefully
  handle 404s because fetchJson swallows the error before SWR can set it.

6. REMAINING ISSUES (not fixed here)
--------------------------------------
  a) fetchJson swallows errors — SWR never gets to set error state, so
     the nice in-page error handler (lines 167-218) never triggers. The
     Sentry ErrorBoundary catches the crash instead, showing a generic
     unhelpful message. Fix: fetchJson should re-throw for SWR to catch,
     or getReport should handle fetchJson returning false.

  b) 2931 legacy reports have no sections.filters and no reportType.
     Opening any of them may crash or show empty charts. These are from
     the old report schema before the sections migration.

  c) The ResponseError class has .response (the full Response object)
     but the [id].tsx checks (reportError as any)?.status — it should
     check .response?.status instead.
