VERDICT: *** CRITICAL MISMATCH ***

  The API returns EzProtectDashboardSummary:
    { locationId, generatedAt, totalEvents, latestOccurredAt, windows }

  But the page expects FacilityDashboardResponse:
    { devices, positives, invalids, errors, pmTests, windows }

  Specific mismatches:
    a) Page expects "devices" array       --> API does NOT return this
    b) Page expects "positives" object    --> API does NOT return this
    c) Page expects "invalids" array      --> API does NOT return this
    d) Page expects "errors" array        --> API does NOT return this
    e) Page expects "pmTests" array       --> API does NOT return this
    f) Page expects WindowSummary with fields: positiveCount,
       invalidCount, errorCount           --> API WindowSummary has only:
       windowDays, totalEvents, byResultState (no positiveCount etc.)
    g) API returns locationId, generatedAt, totalEvents,
       latestOccurredAt                   --> Page does NOT read any of these

  Root cause: facility.tsx was built expecting a dedicated facility
  dashboard shape (likely designed before the API was implemented or
  copy-pasted from a mockup), but the API endpoint reuses the same
  GetEzProtectDashboardUseCase as /dashboard, which returns the simpler
  EzProtectDashboardSummary structure.

  Impact: The facility.tsx page will render with all empty/zero data.
  dashboard.devices will be undefined, .length will throw. The page
  will likely show "No devices found" and zero values everywhere.

CRITICAL ISSUES (will cause visible bugs / blank pages):

  1. facility.tsx: Entire page is built for a response shape that does
     not exist. The API reuses GetEzProtectDashboardUseCase which returns
     {locationId, generatedAt, totalEvents, latestOccurredAt, windows}
     but the page expects {devices, positives, invalids, errors, pmTests,
     windows}. Every section will be empty or crash.

  2. devices.tsx: API returns DeviceInfo[] (bare array) but page expects
     {devices: DeviceInfo[]}. Also field name mismatches:
     calibrationStatus vs lastCalibrationStatus,
     pmStatus vs lastPmStatus, id vs (missing).

  3. alerts.tsx (Rules): API returns AlertRule[] (bare array) but page
     expects {rules: AlertRule[]}. Also _id vs id, faqLink vs faqLinks.

  4. alerts.tsx (History): API returns {alerts: [...]} but page reads
     {history: [...]}. Also field renames: date/sentAt, trigger/triggerType,
     id/_id.


RECOMMENDED FIXES (priority order):

  1. facility.tsx: Either create a dedicated GetFacilityDashboardUseCase
     that returns the expected shape (devices, positives, invalids, errors,
     pmTests, windows with positiveCount/invalidCount/errorCount), OR
     rewrite facility.tsx to use the EzProtectDashboardSummary shape.

  2. devices.tsx: Either wrap the API response as {devices: result} in
     the use case, OR change the page to read the bare array. Fix field
     names: lastCalibrationStatus -> calibrationStatus, lastPmStatus ->
     pmStatus. Add "id" field to DeviceInfo (could use deviceSerialNumber).

  3. alerts GET: Either wrap as {rules: result} in the use case, OR
     change page to read bare array. Map _id to id. Rename faqLink(s).

  4. alert-history: Rename response key "alerts" to "history", OR change
     page to read "alerts". Map sentAt->date, triggerType->trigger,
     _id->id.

  5. alerts POST: Verify fetchJson handles empty 201 responses correctly.
     Consider returning {created: true} without the URL to avoid the
     Endpoint framework's res.created() interception, or adjust the
     framework check.
