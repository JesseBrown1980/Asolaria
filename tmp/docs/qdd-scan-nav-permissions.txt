4. NAV FILTER (filterByAccess.ts)
================================================================================

File: src/hooks/filterByAccess.ts

Flow:
  1. buildNavItems(t) creates all routes
  2. getNavItems(user, location, t) calls filterByAccess(user, navItems, location)
  3. filterByAccess checks hasPermission(user, locationId, domain, action)
     for every item with permissionDomain set

       restrictedUserNavItems = ['/', '/sample-scheduler', ..., '/admin/billing']

GAP: /ez-protect is NOT in the restrictedUserNavItems whitelist.
     Even if a restricted_user is explicitly granted ezProtect:view,
     the nav entry will be FILTERED OUT by the whitelist on line 134.
     This is CORRECT behavior (restricted_user should not see EZ Protect).

5. PERMISSIONS UTILITY (permissions.ts)
================================================================================

File: src/utils/permissions.ts

hasPermission(user, locationId, domain, action, resource?, resourceId?):
  - Looks up user.permissions[] for matching locationId
  - Checks the permission domain property (e.g. perm.ezProtect.action)
  - 'manage' grants both manage and view
  - 'view' grants view only

NOTE: ezProtect is typed as OPTIONAL in UserPermissionView (line 20):
    ezProtect?: PermissionView;
  If the property is missing from a permission record, hasOwnProperty returns
  false -> returns false. This is safe but different from other domains like
  'reports' which are required.

GLOBAL FALLBACK ISSUE (lines 97-113):
  When locationId='global' and no permission record matches, there is a
  hardcoded fallback for company_admin/facility_admin that grants access to:
    reports, categories, organisms, zones, users, testResults, billing
  There is a special check for 'novalum' (line 110-112).

  GAP: There is NO global fallback for 'ezProtect'.
  If a company_admin has no explicit global permission record with
  ezProtect:view, they will NOT see EZ Protect in the nav when viewing
  the global/corporate scope. This is likely INTENTIONAL (opt-in module),
  but it means the corporate dashboard at /ez-protect requires an explicit
  global permission grant.

6. EZ PROTECT ENTITLEMENT LOGIC (utils/ezProtect.ts)
================================================================================

File: src/utils/ezProtect.ts

Three exported functions:

  isEzProtectRolloutEnabled():
    Returns true if NEXT_PUBLIC_FEATURE_CHARM_EZP_MODULE='true'
                  OR FEATURE_CHARM_EZP_MODULE='true'
    NOTE: This function is DEFINED but NOT USED in any page or nav logic.
    The module access is purely permission-backed (see below).

  hasEzProtectEntitlement(user, location):
    1. Checks facility-specific permission: hasPermission(user, locationId,
       EzProtect, View)
    2. Falls back to global permission: hasPermission(user, 'global',
       EzProtect, View)
    Returns true if either passes.

  isEzProtectModuleEnabled(user, location):
    Simply delegates to hasEzProtectEntitlement(user, location).
    The rollout flag is intentionally NOT gating access (comment on line 56-58
    explains: "The rollout flag is still useful for evidence/planning, but it
    must not imply reachability on its own").

12. IDENTIFIED GAPS & ISSUES
================================================================================

GAP-1: DEAD ROLLOUT FLAG
  isEzProtectRolloutEnabled() is defined and tested but NEVER called in
  production code. isEzProtectModuleEnabled() skips it entirely. The flag
  env vars NEXT_PUBLIC_FEATURE_CHARM_EZP_MODULE / FEATURE_CHARM_EZP_MODULE
  have zero runtime effect. Either remove the dead code or wire it back in
  if planned for future gating.

GAP-2: DUPLICATE ICON
  EZ Protect uses DeveloperModeIcon, same as Novalum. Users with both
  modules enabled see two identical icons in the sidebar.

GAP-3: OPTIONAL TYPING ON ezProtect PERMISSION
  In permissions.ts UserPermissionView, ezProtect is typed as optional
  (ezProtect?: PermissionView). If a legacy permission record lacks the
  property entirely, hasPermission falls through to hasOwnProperty=false
  and returns false. This is safe but means older records created before
  EzProtect was added will silently deny. No migration concern flagged,
  but worth verifying existing prod data includes the field.

GAP-4: NO GLOBAL ADMIN SHORTCUT
  Unlike novalum (which has a special global check at line 110-112 in
  permissions.ts), ezProtect has no such shortcut. Company/facility admins
  MUST have an explicit global permission record with ezProtect:view to
  see the corporate dashboard. If this is intentional, fine. If not, add
  a parallel check.

GAP-5: INGEST API REQUIRES 'manage' BUT NO NAV DISTINCTION
  The /api/ez-protect/ingest endpoint requires Manage-level permission,
  but the nav only checks for View. Users who can see EZ Protect in nav
  but only have 'view' permission will get API errors if they try to
  ingest data. The UI should either hide ingest controls for view-only
  users or surface a clear error.

GAP-6: NO .env DEFAULTS FOUND
  No .env or .env.example file in web-ebacmap to document expected values
  for NEXT_PUBLIC_FEATURE_CHARM_EZP_MODULE. New developers won't know
  this flag exists.
