CRITICAL ISSUES
---------------

[C-01] Notification.clientId references WRONG model
  File: Notification.ts line 33
  Schema says: ref: 'TestDefinition'
  Should be: ref: 'Client'
  Impact: Any .populate('clientId') on Notification will pull a TestDefinition
          instead of a Client. The interface correctly says clientId: Types.ObjectId
          but the ref is wrong.

[C-02] TestDefinition.organism references non-existent collection 'Organisms'
  File: TestDefinition.ts line 54
  Schema says: ref: 'Organisms' (plural)
  Should be: ref: 'Organism' (singular)
  Impact: .populate('organism') on TestDefinition will fail silently or throw.
          Note: organismId (line 40) correctly references 'Organism'.

[C-03] Duplicate category/organism fields in TestDefinition
  File: TestDefinition.ts lines 39-54
  There are both `categoryId` (ref:Category) and `category` (ref:Category),
  and both `organismId` (ref:Organism) and `organism` (ref:'Organisms').
  This is confusing and the 'organism' variant has the wrong ref.
  Impact: Code may use either field inconsistently. Should consolidate.

[C-04] defaultValue vs default — Mongoose ignores 'defaultValue'
  Affects: Client.ts (numLocations, isDeleted, imported, ssoEnabled, forceSSO)
           Location.ts (isDeleted)
           Site.ts (isComposite, active, isDeleted)
           Category.ts (isDeleted)
           Organism.ts (isDeleted)
           Product.ts (isLocationSpecific, isDeleted, isActive, isAssociateUser)
           SiteGroup.ts (isDeleted)
           FacilityMap.ts (isDeleted)
           BlackoutDate.ts (isDeleted)
           TestDefinition.ts (isDeleted)
           TestResult.ts (isDeleted)
           TestResultRead.ts (isDeleted)
           PendingTestResult.ts (isDeleted)
           Capa.ts (isDeleted)
           SwabSchedule.ts (endDate, isDeleted, useGroups, randomize,
                           repeatRandomized, pendingChanges)
  Mongoose uses `default`, not `defaultValue`. These defaults are silently
  ignored, meaning new documents will NOT get these default values.
  This is the single most pervasive bug across the codebase.

[C-05] optional / allowedValues / decimal — non-Mongoose schema keywords
  Affects: TestResult.ts, PendingTestResult.ts, TestDefinition.ts,
           TestResultRead.ts, Site.ts, ActivityLog.ts, Stats.ts
  Mongoose does not recognize `optional`, `allowedValues`, or `decimal`
  as schema type options. These are likely leftovers from a SimpleSchema/
  Meteor migration and are silently ignored.
  - `optional: true` does NOT make the field optional (it already is by default)
  - `allowedValues` does NOT validate — use `enum` instead
  - `decimal: true` does NOT enforce decimal — use mongoose-float or Decimal128

[C-06] autoValue functions — non-Mongoose pattern
  Affects: ActivityLog.ts (date), Migration.ts (date), Stats.ts (date),
           TestDefinition.ts (qualitativeTarget, quantitativeTarget, quantitativeLimit)
  Mongoose does not have `autoValue`. These functions are never called.
  Use `default` for defaults, or pre-save middleware for computed values.


HIGH ISSUES
-----------

[H-01] EzProtectEvent unique index includes nullable sampleId
  File: EzProtectEvent.ts line 161-164
  The unique composite index {deviceSerialNumber, completedAt, sampleId}
  is NOT sparse. If two events from the same device at the same time both
  have null sampleId, only one can be stored. This is documented as
  intentional but may cause silent data loss for batch readings.

[H-02] No indexes on many high-traffic query patterns
  - Capa: no index on clientId, location, or status — queries will table-scan
  - SwabSchedule: no index on clientId+locationId — O(n) scan for schedule lists
  - TestResult: only text index on 'name' (which doesn't exist in schema!)
    Missing: {client:1, location:1, sampleDate:-1} for the primary query path
  - PendingTestResult: only text index on 'name' (doesn't exist!)
    Missing: {client:1, location:1} at minimum
  - Channel: no indexes at all
  - FtpImportLog / FtpExportLog: no index on locationId
  - Queue: no indexes — needs {nextRunAt:1, lastStatus:1} for job polling

[H-03] Text indexes on non-existent 'name' field
  - ActivityLog: index on { name: 'text' } but schema has no 'name' field
  - QueueLog: index on { name: 'text' } but schema has no 'name' field
  - Migration: index on { name: 'text' } but schema has no 'name' field
  - TestResult: index on { name: 'text' } but schema has no 'name' field
  - PendingTestResult: index on { name: 'text' } but schema has no 'name' field
  These indexes exist but match nothing — wasted storage and write overhead.

[H-04] RateLimit model has no TTL index
  File: RateLimit.ts
  The 'expires' field exists but there is no TTL index to auto-delete expired
  rate limit entries. The collection will grow unbounded.

[H-05] strict:false on most schemas is a risk
  28 of 46 schemas use strict:false. This means any arbitrary field can be
  written to the database. Potential for:
  - Schema drift (fields in DB not in code)
  - Injection of unexpected fields via API
  - Difficulty in schema migration
  Notable: ALL EzProtect models use strict:false despite being new code.

[H-06] User model has no index on client field
  File: User.ts
  The most common query pattern is "find users by client" but there is no
  index on {client:1}. Only a compound text index on name/email fields.

[H-07] Location model has no index on clientId
  File: Location.ts line 156-157
  The clientId+_id unique index is commented out. Only a text index on name
  exists. "Find locations by client" will table-scan.

[H-08] TestResultRead has NO indexes at all
  File: TestResultRead.ts
  This is a read-optimized denormalized view but has zero indexes.
  Missing at minimum: {client._id:1, sampleDate:-1} and
  {location._id:1, sampleDate:-1}.


MEDIUM ISSUES
-------------

[M-01] EzProtectEvent.clientId and locationId are optional
  Both are typed as optional in the schema (no 'required'). However, use cases
  always set them during ingestion. If ingestion code changes, events could be
  stored without client/location linkage, breaking all dashboard queries.
  Recommend: add required:true to both fields.

[M-02] EzProtectAlertHistory stores alertName as a string copy
  If the alert rule name is updated, the history retains the old name.
  This is likely intentional for audit purposes but should be documented.

[M-03] Tour marker positions have inconsistent types
  File: Tour.ts
  - Root markers: position.yaw is String, position.pitch is String
  - Node markers: same String types
  - Node links: position.yaw is Number, position.pitch is Number
  - Interface: yaw:number, pitch:number everywhere
  The schema stores strings but the interface expects numbers.

[M-04] Capa AssignedAction uses 'require' instead of 'required'
  File: Capa.ts line 117
  `require: true` is not valid Mongoose. Should be `required: true`.
  The assignedUserId field will accept null values despite the intent.

[M-05] Client model missing subscriptionFeatures in schema
  File: Client.ts
  The DbClientSubscriptionFeatures interface includes ezProtect, testDefinitions,
  autoDisable, ssoEnabled, and many other feature flags. But the schema (line 70-131)
  does NOT define subscriptionFeatures at all. These are only saved because
  strict:false is set. If strict were ever changed to true, all feature flags
  would be silently dropped on save.

[M-06] Location subscriptionFeatures.autoDisable is at wrong nesting level
  File: Location.ts line 141
  autoDisable is inside subscriptionFeatures in the schema, but in the
  DbLocation interface (line 50), autoDisable is a top-level field.
  Type mismatch between interface and schema.

[M-07] Queue model defines _id in schema
  File: Queue.ts line 32
  Explicitly defining _id: Schema.Types.ObjectId can cause issues with
  Mongoose's built-in _id handling. Usually unnecessary.

[M-08] ReportToken stores report as String, not ObjectId ref
  File: ReportToken.ts
  The report field is a plain String, not an ObjectId reference. Cannot
  use .populate() and no referential integrity.

[M-09] ActivityLog 'option' typo
  File: ActivityLog.ts line 56
  `option: true` should be `optional: true` (which itself is not valid
  Mongoose — should be removed entirely since all fields are optional by default).
