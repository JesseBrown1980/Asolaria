2. $match FILTER
   The pipeline builds a dynamic query object:

     if (filter.locationId) query.locationId = filter.locationId;

5. locationId / clientId TYPE MISMATCH — THIS IS THE BUG
   Schema definition (EzProtectEvent.ts lines 150-151):
     locationId: { type: Schema.Types.ObjectId, ref: 'Location', required: true }
     clientId:   { type: Schema.Types.ObjectId, ref: 'Client',   required: true }

   Both fields are stored as MongoDB ObjectId in the database.

   How the UseCase calls getDevices (GetDeviceHealth/UseCase.ts):
     filter.clientId  = ctx.user.clientId;   // string (from UseCase.ts user interface)
     filter.locationId = request.locationId;  // string (from yup schema / query param)

   How getDevices builds the $match:
     query.locationId = filter.locationId;  // passes raw string
     query.clientId   = filter.clientId;    // passes raw string

   THERE IS NO ObjectId CONVERSION.

   MongoDB aggregation pipelines bypass Mongoose's automatic casting.
   Mongoose .find() auto-casts string → ObjectId for fields defined as
   ObjectId in the schema, but .aggregate() does NOT.

   So the $match is:
     { clientId: "69c41938d84980e337ac77cd", locationId: "69c41938d84980e337ac77cf" }

   But the documents contain:
     { clientId: ObjectId("69c41938d84980e337ac77cd"), locationId: ObjectId("69c41938d84980e337ac77cf") }

   String "69c41938d84980e337ac77cd" !== ObjectId("69c41938d84980e337ac77cd")
   Result: $match returns 0 documents. getDevices() returns [].

6. TIME WINDOW
   No. The $match has NO completedAt filter. All events are scanned.
   The 24-hour window is only used post-aggregation to set status to
   "online" or "offline".

   Compare with getDashboardSummary (line 211) and getCorporateDashboard
   (line 248) which both add completedAt: { $gte: thirtyDaysAgo } to
   their $match. getDevices does not.

CONFIRMED BUG
=============
The aggregation pipeline passes string IDs into $match but the database
stores ObjectIds. MongoDB aggregate() does not auto-cast. This means:

  - 300 events exist with the correct clientId and locationId as ObjectIds
  - 10 unique deviceSerialNumber values (SN-1001 through SN-3005)
  - getDevices() returns [] because the string/ObjectId mismatch finds nothing

FIX
===
Import mongoose Types and cast before building query:

  import { Types } from 'mongoose';

  const query: any = {};
  if (filter.locationId) query.locationId = new Types.ObjectId(filter.locationId);
  if (filter.clientId)   query.clientId   = new Types.ObjectId(filter.clientId);

Same bug likely exists in listNormalizedEvents() (line 139-140) BUT
that method uses .find() which benefits from Mongoose auto-casting,
so it works. Only the aggregate()-based methods are affected.

Also affected: getCorporateDashboard() (line 248) uses aggregate with
{ clientId } as a raw string — same bug pattern. getDashboardSummary()
(line 213) uses .find() so Mongoose auto-casts and it works.
